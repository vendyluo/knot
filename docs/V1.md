# Knot v1：保存、找回、到時提醒

狀態：產品與行為規格，2026-09-12。**不是已發布功能清單，也不是部署指示。**

實作進度（2026-09-12）：單次 `@notify` 規則版及記事點擊取回已部署至作者的試用 Worker，提醒已啟用；尚未完成 LINE 實機／計費驗收。Repository 預設仍停用提醒。後續加入的選用 Workers AI 時間解析尚未部署，僅完成 mock 整合測試，不代表真實模型品質已驗收。其他 v1 工作仍依下表區分。[啟用與排障](SETUP.md#11-optional-reminders)。

## 定位與證據

Knot 是自架的 LINE 記憶工具：重要的事存得下、找得到，需要時會提醒。
不做大型 SaaS、通用 AI 助理、任務管理平台或通知框架。

- 作者第一手回饋：目前保存效果好，但從列表輸入記事 ID 取回不夠快；希望加入 `@notify 時間 事項`。
- 外部需求：調查時沒有公開 issues，Discussions 無公開可讀入口；沒有確認外部部署或活躍使用者。
- Threads 約 2.3 萬瀏覽、GitHub 12 stars／1 fork 是關注訊號，不是需求或使用證據。
- 本文件的 UX、可靠性與成本規則是產品決策；不能寫成外部使用者已要求的功能。

## 現況與 v1 邊界

| 能力 | 本文件建立時狀態 | v1 完成條件 |
| --- | --- | --- |
| 明確保存文字、媒體、對話 | 已有 | 保存成功與未完成／失敗可辨識 |
| 列表點記事、成功卡「查看這則」 | 已部署作者試用 Worker；未完成 LINE 手機驗收 | 不必輸入 ID；舊卡片仍能操作 |
| 找回較舊記事與完整內容 | 最近十筆＋ID；文字顯示上限 3,000 字，附件前十個 | 不知道 ID 也能瀏覽較舊記事；截斷有提示及完整取回途徑 |
| 單次提醒 | 規則版已部署並啟用於作者試用 Worker；repo 預設停用，待實機驗收 | 建立、查看、取消、到期 Push、失敗可查 |
| 備份還原 | 尚無完整演練文件 | 用假資料驗證 D1＋R2 可一起還原，留下操作步驟 |

搜尋不是 v1 必要條件；較舊記事先以簡單分頁解決。每項分開交付，不要求同一個變更完成全部。

v1 不包含：週期提醒、貪睡、行事曆同步、OCR、標籤系統、LIFF 後台、外部 webhook 通知 API、通知 token、原生 LINE 舊資料自動遷移。
時間解析預設 `rule`，部署者可選 `ai`：規則優先，只有不支援的寫法交給 Workers AI；不是通用助理，也不讓模型操作排程或改寫事項。AI 只見該指令與基準時間，仍可能解讀錯誤，建立回執要求核對時間與事項。失敗不建立提醒；推論有額外延遲與可能費用。[設定與隱私](SETUP.md#choose-rule-or-ai-time-parsing)。
README 的其他延伸構想不等於 v1 承諾；投票與日期投票也不在本輪範圍。

## `@notify`：輸入一次就設定好

以下命令已在本機版本實作；部署並啟用後才可使用建立提醒功能。未啟用仍可查列表與取消既有提醒：

```text
@notify 30分鐘後 關烤箱
@notify 明天 09:00 帶健保卡
@notify 2026-09-20 18:30 訂餐廳
@notify 列表
@notify 取消 42
@notify 說明
```

- 預設規則版只接受正整數「N分鐘後」、「明天 HH:mm」、「YYYY-MM-DD HH:mm」與非空白事項；其他寫法提供上述例子，不猜意思。
- 規則版不接受只有「九點」「下週」的含糊時間、無效日期或已過去的絕對時間。選用 AI 也會驗證日期與範圍，並要求模型拒絕含糊時間；語意是否真的明確仍無法由格式驗證保證。
- v1 統一使用 `Asia/Taipei`；回覆必須顯示完整日期、時間與時區。資料庫存 UTC 時間。
- 相對時間與「明天」以原始 LINE event 時間為基準，不以重送到達時間重新計算；重送不能把提醒向後移。
- 時間明確就直接建立，不增加一次「確定嗎」。只有持久化成功後才回「已設定」。
- 不必先建立記事；提醒內容不自動成為永久記事。

假設在 2026-09-12 輸入 `@notify 明天 09:00 帶健保卡`，回覆內容應包含：

```text
已設定提醒 #42：帶健保卡
2026/09/13（日）09:00 · 台北時間
提醒位置：這個私人聊天室
〔取消提醒〕〔待提醒列表〕
```

取消與列表操作放在卡片內，不只放會隨新訊息消失的 quick reply。
按鈕與文字指令必須使用同一套權限及狀態檢查。修改先採取消後重設，不建立多輪編輯流程。

## 提醒給誰、誰能取消

- 私人聊天建立：Push 到該私人聊天室；長期使用應先將自架 OA 加為好友。
- 群組建立：Push 到原群組，收據明寫「此群組所有成員可見」，不私訊建立者、不跨聊天室選收件者。
- 群組提醒列表是共享的。v1 採共享聊天室規則：該群組成員可取消該群組提醒；不是只有建立者能取消。
- 每次查看、取消都從目前 webhook source 判斷 workspace，不能信任按鈕攜帶的目的地或只憑 ID 授權。
- 取消尚未領取的提醒後，不得再發送。已開始發送時回覆「已開始發送，無法保證取消」，不回假成功。
- 重複取消是無副作用操作；已取消、已送交 LINE、找不到或無權限，都有明確且不洩漏其他聊天室內容的回覆。
- OA 被封鎖、退出群組或裝置關閉通知時，不承諾使用者一定收到。此功能不是緊急警報或準秒鬧鐘。

## 排程：一個 Cron，提醒存在 D1

沿用 Worker＋D1；提醒本身不需要新增 R2 媒體物件或 Durable Objects。

```text
LINE 命令 → 解析／驗證 → D1 保存 → Reply 回覆設定結果
                              ↓
每分鐘 Cron → 原子領取到期提醒 → LINE Push → D1 記錄結果
```

- 固定一個每分鐘 Cron，不隨每筆提醒建立或修改 Cloudflare Cron 設定。
- 每次以索引查詢到期且可重試的工作，有限批次處理；不掃描全部歷史資料。
- 正常情況以分鐘級處理到期工作，不保證 60 秒內送達；尖峰、服務故障與 LINE 投遞都可能延遲。
- 提醒保存 workspace／目的地、事項、到期時間、原始事件識別、狀態及必要發送 metadata；具體 schema 在實作時設計。
- 原始 webhook event 識別需唯一，重送同一建立命令不新增提醒；使用者另傳一則相同文字是新的明確操作。

## 不漏報失敗，也不因重試一直轟炸

建議狀態語意：待發送、發送中、已送交 LINE、已取消、失敗、已過期、結果未確認。
「已送交 LINE」只代表 API 接受，不代表送達或已讀。

- 領取工作使用原子條件更新與可恢復的租約，避免重疊 Cron 同時取得同一工作。
- 第一次 Push 前持久化固定 UUID retry key 與不可變的收件者／payload；同一發送重試不得更換。
- 網路逾時、暫時性伺服器錯誤採有限次數退避重試；已接受或同 key 已接受的回應不重送。
- API 已接受但 D1 更新失敗：恢復後沿用原 key，不能直接產生新 Push。
- 無效憑證、額度用盡等錯誤須分類記錄，不以高頻重試掩蓋；不要依賴另一則 Push 才能告知 Push 失敗。
- 超過 LINE retry key 安全期限仍無法確認結果時，標為結果未確認，不自動換 key 補發。
- 過時提醒不能無限制補發。補發須標明原訂時間；超過補發期限標為已過期。
- 使用者可從列表查看近期失敗／過期狀態；管理者可從不含私人事項的結構化 log 排障。

本次實作採用以下固定參數，不新增多組設定開關：

| 參數 | 實作值與取捨 |
| --- | --- |
| 最晚補發期限 | 到期後 1 小時（包含邊界）；分鐘級處理，不能作緊急鬧鐘 |
| 事項長度、最遠排程日期、每 workspace 待發上限 | 500 Unicode 字元、365 天、100 筆 pending/sending；不等於全站防濫用或費用上限 |
| 新命令最長延遲 | 原始 LINE event 超過 1 小時才首次抵達時拒絕；既有 message ID 回傳原收據，避免日後清理後重建舊排程 |
| 發送批次與租約 | 每 tick 最多 10 筆，逐筆原子領取；租約 120 秒，HTTP timeout 10 秒 |
| 退避與次數 | 網路錯誤／5xx 最多 6 次總嘗試，間隔 60、120、240、480、900 秒；4xx 停止自動重試 |
| 終態資料保留期 | 30 天後每 tick 最多清理 100 筆，取消不代表立即抹除內容 |
| 列表 | 每頁 5 筆完整事項，待提醒優先，其後為近期終態紀錄；翻頁期間狀態改變可能造成項目移動，可回第一頁更新 |

去重使用原始 LINE message ID；同一訊息不建立第二筆，不同訊息即使文字相同仍視為新操作。Push payload 第一次發送前保存，此後不改內容或收件者；延遲標記以第一次嘗試時判定，重試不改 payload。
Cron 在提醒關閉時仍執行過期與清理；關閉期間待提醒可能過期，重開後仍在補發期限內者可能送出。已領取工作即使在重試間隔也不回覆取消成功。

## 費用、啟用與資料隱私

- 提醒預設關閉，由自架者明確啟用；公開測試 OA 不自動開放無限制提醒。
- 設定、列表、取消用 Reply API；到期用 Push API，消耗各自 OA 的額度。
- 群組 Push 依接收人數計算，不是每群組只算一則。建立當下不能保證未來仍有額度。
- 每分鐘 Cron 在 30 天約執行 43,200 次，另有 D1 讀寫與 LINE 費用；不承諾完全免費。
- 啟用驗收包含測試 Push、配額檢查方式與失敗排查；未啟用時 `@notify` 必須說明不可用，不接受後沉默。
- 提醒事項及目的地會保存在自架者的 D1，直到終態保留期結束；取消是停止提醒，不等於立刻抹除所有副本。
- 原始命令仍沿用既有短期快照政策；日誌、備份與 LINE 聊天訊息另有各自保留邊界，不能宣稱取消會刪除所有地方的內容。
- 正式事件內容、token、user/group ID 不可出現在公開範例或故障分享；使用合成資料。

## 驗收：驗行為，不只看成功卡

- [ ] 三種時間格式解析正確；午夜附近、跨月／跨年、無效日期與過去時間有測試。
- [ ] 保存成功前不顯示「已設定」；時間、事項、提醒目的地可直接核對。
- [ ] 同 event 重送僅一筆提醒，到期時間不漂移；不同 event 的相同文字仍可各自建立。
- [ ] 個人／不同群組不能互看或取消；群組內共享取消符合本文規則。
- [ ] 取消與 Cron 領取同時發生時，只有一種合法結果，不出現「已取消」後又開始發送。
- [ ] 重疊 Cron、程序中斷、LINE 接受後 D1 寫入失敗，皆不因更換 retry key 造成重複發送。
- [ ] 逾時、配額錯誤、憑證錯誤、過期工作有可查狀態；不宣稱 API 接受等於已送達。
- [ ] 手機實際檢查私人與群組卡片、長事項、插入新訊息後操作舊卡片。
- [ ] 到期 Push 用拋棄式測試 OA 驗證；記錄時間與計費差異，不使用正式私人事項。
- [ ] 較舊記事可瀏覽、完整內容可取回、D1＋R2 備份還原通過假資料演練，才稱為 v1 完整流程。
